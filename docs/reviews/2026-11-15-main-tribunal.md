# Tribunal — main (18 unpushed commits, base origin/main) — 2026-11-15

> Hater → judge → verdict. Files: 24 (23 changed source files, tests excluded on request, plus assets/js/connection-notice.js named by the integration review). Accusations: 58. Confirmed weak: 28.

## ⚖️ Verdict — genuinely weak spots

The 18 commits are sound at their core: tests pass, the server stays the referee, report and block are server-checked, the seat token is random, compared in constant time and rotated, and migrations now run whole. The weak spots cluster around **two seams the new features opened**: (1) *the lifetime of a seat on the client* — when a page should forget it, and what a late `seatResumed` may overwrite; (2) *client and server windows that do not match* — 30 reportable messages vs 100 shown, a resumed page's draw/clock/repetition state vs the server's. Most issues are narrow races or stale UI, not data loss or security holes; none is critical.

Duplicates found by several reviewers are merged below (all their ids are listed).

### Major
- **[major] server/chat.js:chatReport 157-159 + assets/js/game-chat.js:reportButton 136-144** (chat c1, game-chat c1) — The server keeps the last 30 messages (both players) but the page shows a Report button on up to 100; reporting an older message (or an unknown id) is dropped silently, and the button the page disabled before emitting stays greyed out forever, with no report saved and no feedback. On a safety feature.
  _Fix:_ server emits `chatNotice { reason: 'report-expired', messageId }` (id validated as an integer) when the message is gone; page re-enables or replaces the button with a text, and only offers Report on messages still reportable (last 30), or keeps as many server-side as it shows.

A player who quits mid-game and reloads within the hold is put back into the game they quit (and the opponent waits 30 s instead of winning at once, contrary to known-limits' "quitter reste un abandon immédiat").
  _Fix:_ route Quit Game through `leaveGame()` (with a confirm if a game is in progress); add an e2e test: quit online mid-game, reload, no `seatResumed`.
- **[major] server/socket-utils.js:seatKeeper.resume 300-309** (socket-utils c1) — The takeover never removes the previous socket from the Socket.io room. Socket.io recovery rejoins a recovered socket to all its saved rooms (verified in node_modules/socket.io), so in the duplicated-tab case the original tab can come back, keep receiving every room broadcast, never get `seatLost`, and show a seat whose actions are silently dropped. Narrow trigger, same player only.
  _Fix:_ keep `previous = room.players[player]`; `nsp.in(previous).socketsLeave(room.id)` and `nsp.to(previous).emit('seatLost')` before reassigning.
- **[major] games/chessdown/js/network.js:21-32 + games/chesspell/js/online.js:175-198** (network c1, online c1; seat c1 related) — `seatResumed` is applied unconditionally. ### assets/js/connection-notice.js
- **[minor] connection-notice.js watchConnection 'connect' (!socket.recovered → lost()) → seat.js keepSeat (resumeSeat only at load) → games/chessdown/js/network.js:221 onLost** (i2)
  - 🔥 Hater: When a reconnect is not recovered, watchConnection declares the game lost though the server still holds the seat and the new seat token could take it back; and Chessdown's onLost does not forgetSeat (Ches'spell's leaveGame does), so a reload within the hold brings the player back into a game they were told was lost.
  - 💡 Should have been: In the non-recovered branch try resumeSeat with the stored token and only call onLost on resumeFailed; at least make Chessdown's onLost forgetSeat.
  - ⚖️ Judge (❌ not defended — conceded weak): Partly defensible: treating 'not recovered' as lost is a deliberate simplification. In the usual non-recovered cases the seat really is gone: after a server restart the rooms live in memory and disappear, and past the 2 min recovery window the 30 s hold (seatKeeper) has already given the seat up. But there is one real case the hater gets right. The client sees the drop first (network switch, Wi-Fi handover), reconnects before the server's heartbeat notices (~45 s, as docs/known-limits.md admits), and Socket.io recovery fails because the old session was never stored. On the server the seat is still there, then held for 30 s, so resumeSeat with the stored token would win it back. Instead the page says 'could not be resumed' and the opponent wins 30 s later. The 3 x 1 s 'busy' retries in seat.js would not cover a 45 s wait anyway. The second point has no defence: Ches'spell's onLost goes through leaveGame(), which calls forgetSeat('chesspell'), while Chessdown's onLost (network.js:221) never calls forgetSeat('chessdown'). seat.js only forgets on opponentLeft/roomClosed/seatLost, and none of those reach the new socket. So the token stays in sessionStorage, and a reload within the hold brings the player back into a game they were told was lost. That is an unjustified inconsistency between the two games sharing one contract. It is minor in impact, and the reload does more good than harm, but it is inconsistent.
